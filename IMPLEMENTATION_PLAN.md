# План собственного Watch Together

Дата: 28 октября 2026 года.

## 1. Цель и приоритеты

Собственное приложение для просмотра с друзьями на своём сервере. Главный сценарий — YouTube непосредственно внутри сайта, без расширения. Второй сценарий — синхронизация внешних сайтов через собственное расширение браузера.

Рабочее допущение: референс — Watch2Gether (w2g.tv). Изучены публичные инструкции и документация платформ. Официальный публичный репозиторий с полным приложением и инструкцией self-hosting для w2g.tv при поиске не найден; это не доказывает, что его нет. Архитектура ниже — предложение для нашего приложения, а не описание внутренней реализации чужого сервиса.

### Принятые решения для MVP

- Разработка с нуля по публичной документации W2G; чужие приложения не используем как основу.
- Звонки, голос, камеры и демонстрация экрана исключены из проекта, включая последующие этапы. Текстовый чат также исключён из проекта.
- Одна дефолтная комната на весь сервис. Создания, списка, выбора и удаления комнат нет; многокомнатную архитектуру заранее не строим.
- Вход: открыть сайт → ввести код приглашения и имя → попасть в общий просмотр. Регистрация не требуется.
- Для MVP принимаем один общий многоразовый код, задаваемый владельцем через секрет окружения. Код проверяется сервером и обменивается на гостевую сессию; повторно вводить его при каждом переподключении не нужно. Код не передаём в URL и не храним в открытом виде в браузере.
- У всех вошедших участников одинаковые права управления просмотром. Ведущего, назначения ролей и передачи управления нет. Настройка кода приглашения и отзыв сессий выполняются оператором через серверную конфигурацию; отдельная административная роль в интерфейсе MVP не нужна. Ограничиваем попытки ввода кода и задаём срок жизни сессии. Смена кода закрывает новые входы по старому коду; отзыв существующих сессий выполняется отдельно.
- В MVP нет очереди и плейлистов: только одно текущее видео. Новая ссылка заменяет его у всех участников; автоматического перехода к следующему ролику нет.
- Начальная нагрузка: 2–10 друзей в единственной комнате.
- Развёртывание через AppHub. Предварительный рецепт — `docker-postgres`: Docker-сервис на Render + PostgreSQL в Supabase + репозиторий GitHub. Подключения для рецепта доступны по результату list_recipes от 28.10.2026. Ресурсы пока не создавались.

Независимость: собственные исходники, логика просмотра, данные и расширение; размещение MVP у провайдеров через AppHub. Внешняя авторизация, аналитика и CDN собственных ресурсов не обязательны. Docker-образ и стандартный PostgreSQL сохраняют возможность переноса с Render/Supabase на свой сервер. YouTube и другие источники остаются внешними зависимостями. Недоступность YouTube нельзя устранить своим сервером синхронизации.

## 2. Что берём из Watch2Gether

Публично описанные возможности: комнаты по приглашению, гостевой вход, постоянные комнаты, синхронный плеер, поиск и добавление ссылок, плейлисты, предложения видео, роли и модерация. [Официальная инструкция](https://community.w2g.tv/t/how-to-use-watch2gether/736).

Для внешних сайтов W2gSync открывает страницу у каждого участника отдельно и синхронизирует плеер через расширение. При необходимости авторизации каждый входит самостоятельно. Это отдельный режим, который используем как продуктовый ориентир. [Инструкция W2gSync](https://community.w2g.tv/t/how-to-use-w2gsync/8975).

## 3. Первая законченная версия

- Одна готовая приватная комната; вход по коду приглашения и имени без регистрации. До проверки кода состояние просмотра и realtime-соединение недоступны.
- YouTube-плеер внутри комнаты; добавление watch-, youtu.be-, shorts- и embed-ссылок с нормализацией videoId и начального времени.
- Синхронные запуск, пауза, перемотка, смена видео и поддерживаемая скорость.
- Одно текущее видео: новая ссылка от любого участника заменяет ролик у всех. По завершении видео просмотр останавливается.
- Список участников с состояниями подключения, готовности и буферизации.
- Любой участник может выбрать видео, включить, поставить на паузу, перемотать и изменить поддерживаемую скорость для всех. Громкость и полноэкранный режим — локальные настройки каждого.
- Переподключение, вход посреди просмотра и восстановление после обновления страницы.
- Индикатор рассинхронизации, ручная кнопка синхронизации, понятные ошибки источника.
- Адаптивный интерфейс для компьютера и телефона.
- Развёртывание через AppHub; Docker-образ, резервное копирование и возможность переноса на другой сервер.

Поиск YouTube по ключевым словам и расширение не блокируют выпуск первой версии.

## 4. Архитектура

Предлагаемый стек: TypeScript; React + Vite для клиента; Node.js + Fastify + Socket.IO для API и обмена событиями; PostgreSQL для постоянных данных; Docker для поставки; AppHub для создания инфраструктуры и деплоя. В основном размещении HTTPS обеспечивает платформа. Docker Compose — дополнительный способ локального запуска и переноса.

Это один backend-процесс и одна БД на старте. Redis, Kubernetes и микросервисы не нужны до появления измеренной нагрузки. Версии зависимостей выбираем и фиксируем при начале реализации.

Пути данных:

```text
Браузер A ── HTTPS / Socket.IO ──┐
                                ├── Наш backend (Render) ── PostgreSQL (Supabase)
Браузер B ── HTTPS / Socket.IO ──┘

Браузер A ── встроенный плеер ── YouTube
Браузер B ── встроенный плеер ── YouTube
```

Видео не проходит через наш backend: он передаёт команды и состояние.

Структура проекта:

```text
apps/web/             сайт
apps/server/          HTTP API, вход по коду, общий просмотр, синхронизация
apps/extension/       расширение внешнего просмотра
packages/protocol/    схемы команд, событий и версии протокола
packages/sync/        расчёт времени и правила коррекции
packages/adapters/    адаптеры источников и их возможности
infra/               Dockerfile, конфигурация деплоя AppHub, backup/restore
```

Основные данные: GuestSession, PlaybackSnapshot единственной комнаты. Каталог Room, RoomMembership и CRUD комнат в MVP не нужны. Код приглашения хранится как секрет окружения и проверяется сервером. Все действующие гостевые сессии имеют одинаковые права просмотра и управления; сущности ролей и секрет владельца комнаты не нужны. Быстрые телеметрические данные живут в памяти, устойчивое состояние сохраняется при принятых изменениях и контрольных точках.

## 5. Синхронизация

Backend — единственный источник истины о состоянии комнаты. Клиент отправляет намерение, сервер проверяет сессию и команду, последовательно применяет её, увеличивает revision и рассылает результат.

При одновременных действиях сервер задаёт единый порядок: последнее принятое применимое действие определяет состояние. Команды от старой версии видео отклоняются; отключение любого участника не меняет права остальных.

Состояние: mediaId/mediaRevision, playing/paused, position, rate, anchorServerTime, revision. Пока видео играет, ожидаемая позиция равна `position + (estimatedServerTime - anchorServerTime) * rate`; в паузе позиция постоянна.

Обязательные механизмы:

1. Несколько ping/pong-замеров для оценки смещения клиентских часов и задержки; монотонная шкала времени внутри серверного процесса.
2. При входе — полный snapshot и подтверждение готовности плеера; затем выход на текущую позицию комнаты.
3. У команд есть commandId, у медиа — отдельная версия: повтор не выполняется дважды, событие старого ролика не меняет новый.
4. Периодическая проверка позиции; после возвращения вкладки из фона — повторная синхронизация.
5. Разделение пользовательских действий и программного применения состояния, защита от циклов play/pause/seek.
6. Завершение текущего ролика фиксируется сервером однократно; повторные ended не меняют состояние. Автоматического перехода к другому видео в MVP нет.
7. При обрыве связи клиент помечает просмотр как несинхронизированный; после соединения принимает новый snapshot, не выполняет накопившиеся устаревшие команды.
8. После рестарта сервер создаёт новую эпоху синхронизации; восстанавливает последнее видео и позицию в паузе, предлагает продолжить.

Начальные, подлежащие измерению настройки: проверка каждые 2–5 секунд; допуск около 300–500 мс для YouTube; коррекция перемоткой при устойчивом превышении допуска. Цель испытаний — p95 расхождения не более 500 мс после стабилизации на обычных VOD без рекламы, при нормальной сети. Это критерий проверки, не обещание покадровой точности.

Плавную коррекцию скорости на несколько процентов применяем только к адаптерам, которые её поддерживают. YouTube предоставляет ограниченный набор скоростей и перемотку с особенностями ключевых кадров. [YouTube IFrame API](https://developers.google.com/youtube/iframe_api_reference).

Буферизация по умолчанию локальная: отстающий участник догоняет комнату после загрузки. Дополнительный режим «ждать всех» вводим с таймаутом и исключением зависших клиентов; он не должен позволять одному отключившемуся устройству держать комнату в паузе бесконечно.

## 6. Особенности YouTube

- Используем официальный IFrame Player API и видимый встроенный плеер.
- Управление через публичный API; общие кнопки располагаем рядом с плеером. Не перекрываем его интерфейс своими слоями.
- Сохраняем корректные origin и HTTP Referer. Не задаём политику, полностью подавляющую Referer. [Требования к встроенному плееру](https://developers.google.com/youtube/terms/required-minimum-functionality).
- Если браузер запрещает запуск со звуком, показываем локальную кнопку «Подключиться к просмотру» и обрабатываем отказ play. [Ограничения autoplay](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay).
- Обрабатываем удалённые, приватные, регионально ограниченные и запрещённые для встраивания ролики. Ошибка не должна ломать комнату; любой участник может выбрать другую ссылку.
- Реклама и различия доступности могут мешать синхронизации. Проверяем восстановление после рекламы экспериментально; не предполагаем, что публичный API надёжно сообщает её начало и конец.
- Первоначальный сценарий — обычные записи. Прямые эфиры требуют отдельного режима синхронизации по окну доступного эфира и отдельной приёмки.
- Вставка ссылки и воспроизведение через IFrame API не требуют реализации поиска. Поиск по словам добавляем отдельным модулем через YouTube Data API: ключ, квоты и кэш; его отказ не мешает вставлять ссылки.

## 7. Внешние сайты через расширение

Сценарий: любой участник добавляет URL → комната переходит во внешний режим → каждый нажимает «Открыть с расширением» → сайт открывается у каждого в своей вкладке → расширение находит видео и подключает его к состоянию комнаты. Компактная панель на внешней странице показывает комнату и управление.

Первый целевой браузер — Chrome/Chromium с Manifest V3; Firefox — отдельная проверка совместимости позже. Мобильные браузеры в объём первой версии расширения не входят.

Компоненты и границы:

- Popup/страница настроек: адрес собственного сервера, подключённая комната, выдача разрешений.
- Service worker: обмен сообщениями и маршрутизация; проектируем с учётом его остановки и восстановления, не полагаемся на вечную работу фонового процесса.
- Content script: поиск HTMLVideoElement, чтение состояния, применение команд, компактная панель.
- При необходимости отдельный адаптер страницы: iframe, SPA-навигация, замена плеера, несколько видео и собственные API сайта.
- Доступ запрашивается для выбранных сайтов по мере использования; разрешение верхней страницы не означает доступ ко всем вложенным iframe. [Content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts), [разрешения](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions).
- Краткоживущий одноразовый код привязки обменивается на ограниченный токен участника; проверяем отправителя сообщений, origin, схемы и действительность сессии. Токен остаётся в контексте расширения и не передаётся скриптам страницы источника.
- Для первой реализации связь с backend ведём через страницу расширения, связанную с сеансом просмотра; закрытие управляющего контекста явно отключает внешнюю синхронизацию. Поведение при сне вкладок и перезапуске браузера входит в испытания.

Сначала проверяем два-три конкретных сайта и публикуем матрицу поддержки; универсальный HTML5-адаптер — best effort. Список сайтов пока не задан: выбираем перед этапом расширения, поскольку от него зависит объём адаптеров.

Каждый участник самостоятельно авторизуется на источнике. DRM-контент может требовать собственного доступа и CDM; расширение синхронизации не заменяет их. [Encrypted Media Extensions](https://developer.mozilla.org/en-US/docs/Web/API/Encrypted_Media_Extensions_API). Синхронизация разных монтажных версий одного фильма отдельно не гарантируется.

## 8. Дополнительные возможности

После YouTube и расширения: при отдельной необходимости несколько комнат и простой локальный аккаунт владельца; очередь и сохранённые плейлисты; предложения и голосование; удаление участников и отзыв приглашений; реакции; настройки оформления.


Собственные MP4/HLS и локальные файлы — необязательное направление для уменьшения зависимости от источников. HLS можно подключить отдельным адаптером на hls.js с проверкой возможностей браузера. [hls.js](https://github.com/video-dev/hls.js).

## 9. Размещение и эксплуатация

Начальный ориентир для приложения без обработки и ретрансляции видео: Linux-сервер, 1–2 vCPU, 1–2 ГБ RAM, SSD. Это гипотеза до замеров, не гарантированная ёмкость. YouTube-видеотрафик идёт непосредственно к зрителям.

- Основной путь: AppHub, рецепт `docker-postgres`, регион Frankfurt как предварительный выбор. Имя проекта и параметры фиксируем перед созданием ресурсов.
- Один Docker-сервис отдаёт сборку сайта и API/Socket.IO; PostgreSQL подключается через секрет DATABASE_URL. Облачную авторизацию Supabase не используем.
- AppHub создаёт репозиторий и инфраструктуру. После создания читаем конфигурацию рецепта и сохраняем соглашения Dockerfile, деплоя, переменных и миграций при загрузке собственного приложения.
- Проверяем длительные WebSocket-соединения на выбранной платформе, переподключение после рестарта/деплоя и восстановление состояния из PostgreSQL.
- По данным AppHub бесплатный Render засыпает после 15 минут без запросов; первый запуск после сна может занять около минуты. Это отражаем в интерфейсе подключения и проверяем реальным сеансом. По данным AppHub Supabase также может засыпать после недели без активности.
- Критерий готовности деплоя: AppHub показывает успешную сборку, сайт открывается по HTTPS, два клиента проходят вход по коду и синхронно смотрят видео.
- Docker Compose для независимого размещения можно подготовить дополнительно; AppHub не должен становиться зависимостью протокола синхронизации.
- Публичный HTTPS-адрес; по возможности поддержка работы в LAN без обязательного внешнего аккаунта.
- Собственные ресурсы и шрифты включены в сборку; обязательных Google/GitHub login, Firebase, Supabase и аналитики нет.
- Проверка Origin для соединений, серверная авторизация каждой команды, ограничения частоты и размеров команд, проверка пользовательского ввода.
- Код приглашения с достаточной случайностью, ограничение попыток ввода и замена через секрет окружения. Не записываем коды и токены сессий в логи.
- Сервер не загружает произвольные URL ради preview; для метаданных используем проверяемые источники, чтобы не создавать SSRF-прокси.
- Healthcheck, структурированные логи, показатели задержки и рассинхронизации без внешней телеметрии.
- Backup базы и настроек, проверенный restore, миграции и откат версии, инструкция переноса на чистый сервер.
- Сборки расширения выдаём вместе с исходниками; установка распакованной сборки подходит для разработки и небольшой группы, удобный канал обновлений выбирается отдельно.

Оценки ниже — предварительные инженерные диапазоны для одного разработчика с опытом этого стека, включая проверку, без ожидания публикации расширения в магазинах.

| --- | --- | --- | --- |
| 0. Прототип рисков | Два встроенных YouTube-плеера, задержка, seek, autoplay, реклама; проверка AppHub/Render WebSocket | Подтверждены метод коррекции и пригодность размещения | 2–3 дня |

| 3. Готовый сайт | Мобильный интерфейс, деплой через AppHub, backup/restore, документация | Вечер просмотра с друзьями на развёрнутом сервисе | 4–6 дней |
| 4. Расширение | Привязка комнаты, HTML5-адаптер, панель, 2–3 сайта | Пройдена матрица браузеров/сайтов, восстановление сеанса | 8–15 дней |
| 5. Дополнения | Поиск, история, модерация | Возможности проходят отдельную приёмку | 3–6 дней |

Первая законченная YouTube-версия: ориентировочно 3–5 рабочих недель. YouTube + расширение: 5–8 недель. По дополнительным возможностям оценка уточняется отдельно; основная неопределённость — адаптеры внешних сайтов. После этапа 0 оценку пересматриваем.

## 11. Проверка перед выпуском

- Автотесты модели времени, порядка команд, дедупликации, доступа по сессии и завершения текущего видео.
- Вход с правильным и неправильным кодом, ограничение попыток, срок жизни и отзыв сессий, смена кода; запрет чтения состояния просмотра и подключения Socket.IO без сессии.
- Интеграционные тесты сервера с несколькими клиентами и повторным подключением.
- E2E с управляемым тестовым плеером для воспроизводимости; отдельные ручные smoke-проверки настоящего YouTube, не зависящие от него в каждом запуске CI.
- Одновременные pause/seek, смена ролика при буферизации, повторные ended, поздний вход, отключение любого участника, перезапуск backend.
- Задержка и джиттер, потеря связи, фоновая вкладка, сон устройства; повторное присоединение без старых команд.
- Chrome, Firefox, Safari на компьютере; Android Chrome и iOS Safari для основного сайта.
- Ошибки embed, autoplay, реклама, недоступный ролик, некорректные ссылки.
- Замер p95 рассинхронизации после стабилизации и проверка сеанса длительностью 60–120 минут.
- Для расширения: iframe разных origin, замена video в SPA, несколько плееров, отзыв разрешений, закрытие контекста управления.
- Развёртывание с нуля и восстановление из backup на другом сервере.

Рекомендуемый первый результат реализации: сервис, развёрнутый через AppHub, с одной дефолтной комнатой, входом по коду приглашения, YouTube внутри сайта и надёжной синхронизацией одного текущего видео.
